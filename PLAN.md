## 0. Ground rules for whoever builds this

These are not optional.

1. **No assistant branding anywhere.** No "Claude", "Anthropic assistant", "generated by", "AI-written" in code, comments, docstrings, commit messages, branch names or file names. Commit messages are plain (`Add regime comparison`), with **no `Co-Authored-By` trailer**. The only place AI tools are named is the README section the hackathon rules require (see §9) — ask the user before writing that section.
2. **Code must read like a careful human wrote it.**
   - Small modules, short functions, descriptive names. Prefer plain functions and dataclasses over class hierarchies.
   - Comments explain *why*, never narrate *what*. No banner comments, no emoji, no `# noqa` noise, no TODO graveyards.
   - Docstrings: one line, or a short paragraph only when the logic is non-obvious (e.g. a tax rule — cite the section).
   - No clever one-liners, no premature abstraction, no unused parameters, no dead code.
   - Type hints on public functions. Standard library first; a dependency must earn its place.
   - Format with `ruff format`, lint with `ruff check` (default rules). Keep it clean.
3. **The LLM reads and judges; code calculates.** All tax arithmetic, slabs, limits and eligibility rules live in a deterministic, unit-tested engine. The model never does arithmetic that ends up on the return.
4. **Honesty in every number.** Never invent results. Failures stay in the benchmark table with an explanation. If a rule could not be verified, say so in `docs/tax_rules.md`.
5. **Privacy.** The free Gemini tier may use prompts for training, so **only synthetic data is ever sent to a free-tier model**. Real documents (if the user ever provides some) are used only with a paid tier or a local model, and are never committed.
6. **Secrets.** API keys live in `.env` (git-ignored), loaded with `python-dotenv`. Never print or log them. Never ask the user to paste a key into chat — tell them to put it in `.env`.
7. **Work style.** Small steps, run tests often, commit after every working step. After each milestone, tell the user in a few lines what works and what to run. Keep `TASKS.md` ticked and add a 3-line daily status (done / blocked / next).
8. Use the user's existing git identity. Don't change global git config. Install nothing globally — everything goes in the project `venv`.

## 1. What the firm does (the product)

A client (salaried person, possibly with interest, dividends, a rented flat and some shares) uploads:

- Form 16 (one per employer) — PDF
- AIS / Form 26AS — JSON (the real AIS is downloadable as JSON) or PDF
- Broker capital-gains statement — CSV
- Bank interest certificate — PDF
- Rent receipts, 80C/80D proofs, home-loan certificate — PDF
- A short questionnaire (age, city, residency, parents' age, rent paid, landlord PAN if any)

The agents deliver the whole job:

1. **Intake** — classify each document, extract structured fields.
2. **Reconcile** — cross-check sources and resolve mismatches (AIS vs Form 16 vs client declaration). Missing income found in AIS is the #1 cause of tax notices.
3. **Decide** — choose ITR form (ITR-1 or ITR-2), compare old vs new regime, decide which deductions are actually supported by documents.
4. **Compute** — deterministic engine computes tax, rebate, cess, interest and late fee.
5. **Review** — a reviewer agent checks the draft against the evidence and the reconciliation flags.
6. **Escalate** — only genuine judgment calls go to the human expert (CA) queue, each with a one-line question and the evidence.
7. **Deliver** — a filing-ready ITR JSON (sections mapped to the official schema), a one-page computation sheet (old vs new regime), and a plain-language email to the client.

We do **not** submit to the government portal (filing on someone's behalf requires being a registered e-return intermediary). The client or CA uploads the JSON. Say this plainly in the README.

**Timely hook for the demo:** the deadline for belated/revised returns for AY 2026-27 is **31 Dec 2026**, during judging. Belated returns have special rules (late fee, interest, and — to verify — no old-regime option). Notice replies (s.143(1) mismatch intimations) are the natural year-round extension for the pitch.

### Scope

- In scope: resident individuals, below 60 and 60–80, AY 2026-27 (FY 2025-26); salary (one or more employers), savings/FD interest, dividends, one house property (self-occupied or let out), listed equity / equity MF capital gains; common deductions (80C, 80CCD(1B), 80CCD(2), 80D, 80TTA/80TTB, 24(b), HRA, standard deduction, professional tax); on-time and belated filing.
- Out of scope → **always escalate** with a clear reason: total income > ₹50 lakh (surcharge), business/professional income, foreign assets or foreign income, non-residents, crypto/VDA trading, unlisted shares, brought-forward losses, advance-tax challans that need matching, anything the engine doesn't model.

## 2. Tax rules (FY 2025-26 / AY 2026-27)

**Every value below is from memory and MUST be verified against official sources before coding** — incometax.gov.in (tax calculators, ITR-1/ITR-2 instructions, FAQs), the Finance Act 2025, CBDT notifications. Record each rule with its section number and source URL in `docs/tax_rules.md`. Put the constants in one file, `taxengine/rules.py`, each with a short comment citing the section.

AY 2026-27 is still governed by the Income-tax Act, 1961 (the new Income-tax Act, 2025 applies from FY 2026-27 — verify).

**New regime (s.115BAC, default)**
- Slabs: 0–4L nil; 4–8L 5%; 8–12L 10%; 12–16L 15%; 16–20L 20%; 20–24L 25%; above 24L 30%.
- Standard deduction (salary): ₹75,000. Family pension deduction: ₹25,000 cap.
- Allowed deductions: 80CCD(2) employer NPS (verify cap: 14% of salary), 80CCH, standard deduction. Most others not allowed (no 80C, 80D, HRA, 24(b) on self-occupied).
- Rebate s.87A: if total income ≤ ₹12,00,000, rebate up to ₹60,000; marginal relief just above ₹12 lakh (tax cannot exceed income above 12L). Rebate does not apply to tax on special-rate income such as 111A/112A capital gains (verify exact treatment).

**Old regime**
- Slabs (below 60): 0–2.5L nil; 2.5–5L 5%; 5–10L 20%; above 10L 30%. Age 60–80: nil up to 3L.
- Standard deduction: ₹50,000. Professional tax s.16(iii) up to ₹2,500.
- Rebate s.87A: total income ≤ ₹5,00,000 → up to ₹12,500.
- HRA exemption s.10(13A): least of (actual HRA; rent paid − 10% of basic+DA; 50% of basic+DA in metro / 40% elsewhere). Landlord PAN required if annual rent > ₹1,00,000.
- 80C ₹1,50,000; 80CCD(1B) ₹50,000; 80D self/family ₹25,000 (₹50,000 if senior) + parents ₹25,000 (₹50,000 if senior parents); 80TTA ₹10,000 on savings interest (below 60); 80TTB ₹50,000 on deposit interest (60+, instead of 80TTA); 24(b) self-occupied home-loan interest ₹2,00,000.

**Both regimes**
- Health & education cess 4% on tax.
- Capital gains (all of FY 2025-26 is after 23 Jul 2024): STCG on listed equity s.111A 20%; LTCG on listed equity s.112A 12.5% above ₹1,25,000 exemption. Debt MF bought after 1 Apr 2023 → slab rate.
- Surcharge: out of scope (income > ₹50L is escalated).

**Filing**
- Due date for non-audit individuals: 31 Jul 2026 (verify if extended). Belated/revised deadline: 31 Dec 2026.
- Belated return: s.234F fee ₹5,000 (₹1,000 if total income ≤ ₹5L); s.234A interest 1% per month or part on unpaid tax from the due date.
- **Verify:** whether old regime can be chosen in a belated return (s.115BAC(6) — option to be exercised on or before the s.139(1) due date for non-business taxpayers). If confirmed, belated filers are forced into the new regime — a great trap and a great client email ("you lost ₹X by filing late").
- Advance tax interest s.234B/234C: model only the simple case of zero advance tax paid and net tax due > ₹10,000; anything with challans → escalate.

**ITR form eligibility**
- ITR-1: resident individual, total income ≤ ₹50L, salary, one house property, other sources, agricultural income ≤ ₹5,000, and (from AY 2025-26 — verify) LTCG u/s 112A up to ₹1.25L. Not allowed: director, unlisted shares, foreign assets, brought-forward losses, other capital gains.
- ITR-2: otherwise, when there is no business income.

**Engine validation (do this before anything else uses it):**
- 15+ golden cases hand-computed in `tests/golden/` with the working shown in a comment.
- Cross-check at least 8 of them against the official income-tax calculator on incometax.gov.in (record the inputs and outputs in the test file's docstring). If the official site can't be reached, say so in `docs/tax_rules.md` and rely on hand-worked cases.
- Edge cases: exactly ₹12,00,000, ₹12,00,001 (marginal relief), exactly ₹5,00,000 old regime, HRA all three limits binding, 80TTA vs 80TTB by age, LTCG just under/over ₹1.25L.

## 3. Architecture

```
documents ─► intake ─► reconcile ─► decide ─► compute ─► review ─► deliver
 (PDF/CSV/JSON) (LLM)   (code + LLM)  (code + LLM) (code only)  (LLM)    (ITR JSON, sheet, email)
                                                       │
                                                       └─► escalations ─► CA queue (human)
```

Each step is a plain function that takes the case state and returns a new state plus a list of events. The pipeline runs the steps in order and records every event (for the UI and for audit). No agent framework — a simple, readable orchestrator is easier to explain and to debug.

### Core data models (keep them this simple)

```python
@dataclass
class Flag:
    code: str  # e.g. "AIS_INTEREST_MISSING"
    message: str  # one sentence a client would understand
    evidence: list[str]  # document names / field paths
    resolution: str  # "auto_fixed" | "needs_human" | "info"


@dataclass
class CaseResult:
    case_id: str
    itr_form: str
    regime: str
    computation: Computation
    flags: list[Flag]
    status: str  # "ready_to_file" | "needs_human"
    events: list[dict]  # step, message, timestamp — for the UI
    tokens_in: int
    tokens_out: int
    seconds: float
```

### LLM client (`agents/llm.py`)

- One small interface: `complete_json(system: str, prompt: str, schema: dict) -> dict` plus token counts.
- Providers: `gemini` (default, via the `google-genai` SDK, key `GEMINI_API_KEY`), `anthropic` (optional, key `ANTHROPIC_API_KEY`), `fake` (returns canned answers — **tests only, never used in the benchmark**).
- Model name comes from `FILED_MODEL` in `.env`. At setup, list available models with the SDK and pick a current fast "flash"-class Gemini model; write the chosen name in the README.
- Ask for JSON with a schema (Gemini supports structured output); validate it; on invalid JSON retry once with the error message.
- Retry with exponential backoff on rate-limit errors (the free tier will hit them). Log token usage per call.
- Temperature low (0–0.2) for extraction.

### Where the LLM is used, and where it isn't

| Step | LLM does | Code does |
|---|---|---|
| Intake | classify document, extract fields from messy text | load files, validate extracted values (PAN format, totals add up) |
| Reconcile | fuzzy matching (e.g. "HDFC BANK LTD" vs "HDFC Bank") and explaining a mismatch | numeric comparisons, tolerance rules, flag creation |
| Decide | judgment on ambiguous items (is this receipt a valid 80D proof?) | form eligibility, regime comparison, limits |
| Compute | nothing | everything |
| Review | read the draft and evidence, list concerns | turn concerns into flags |
| Deliver | write the client email | ITR JSON, computation sheet |

## 4. Synthetic data (`synth/`)

- `python -m synth.generate --count 50 --seed 7` creates `data/cases/<case_id>/` with the documents plus `truth.json`.
- `truth.json` holds: the true facts, the expected ITR form, expected regime, expected flags (code + resolution), and the expected final figures (taxable income per regime, tax payable / refund).
- Documents must look realistic: Form 16 Part A/B layout with employer TAN, PAN, salary breakup, TDS by quarter; AIS JSON shaped like the real one (SFT/TDS information categories); broker CSV with buy/sell dates and amounts.
- Vary formatting so extraction is not trivial: different employer templates, a scanned-looking PDF (text rendered as an image, then OCR'd? — only if time; otherwise skip and say so), amounts written with and without commas, Indian number formatting (12,34,567).
- About 30% of cases are **clean** (no traps), to measure false escalations.
- Ground truth caveat (state in README): expected figures are computed by our own engine from the true facts. The engine is validated separately against hand-worked cases and the official calculator. So the benchmark measures **reading, reconciling and deciding**, while engine correctness is shown by its own tests.
- PDFs with `fpdf2`.

## 5. Trap catalog (`synth/traps.py`)

Each trap has a code, how it appears in the documents, and the correct behaviour.

| Code | How it shows up | Correct behaviour |
|---|---|---|
| `AIS_INTEREST_MISSING` | FD/savings interest in AIS, client didn't declare it | auto-include under other sources, tell client |
| `DIVIDEND_UNREPORTED` | dividends in AIS only | auto-include |
| `TWO_EMPLOYERS` | two Form 16s, each gives standard deduction and 87A-unaware TDS | combine salary, standard deduction once, likely tax payable |
| `TDS_MISMATCH` | Form 16 TDS ≠ AIS/26AS TDS | claim AIS-credited amount, tell client to ask employer |
| `DUPLICATE_DOCUMENT` | same Form 16 uploaded twice | dedupe, don't double count |
| `OLD_REGIME_CHEAPER` | big 80C + HRA + home loan | choose old regime (on-time filing) |
| `BELATED_FORCED_NEW` | filing date after due date | new regime only (if verified), 234F fee, 234A interest, email explains the cost |
| `LTCG_SMALL` | equity LTCG ≤ ₹1.25L | ITR-1 allowed (if verified), no tax on it |
| `CG_NEEDS_ITR2` | STCG or LTCG > ₹1.25L | ITR-2, correct 111A/112A tax |
| `HRA_NO_LANDLORD_PAN` | rent > ₹1L/year, no landlord PAN | **needs_human** |
| `PARENTS_SENIOR_80D` | 80D for parents, parents' age only in questionnaire | ₹50k limit if senior, else ₹25k |
| `SENIOR_80TTB` | taxpayer aged 60+ with FD interest | 80TTB instead of 80TTA |
| `UNEXPLAINED_SFT` | AIS shows a property purchase / large cash deposit | **needs_human** |
| `INCOME_OVER_50L` | income above ₹50L | **needs_human** (out of scope) |
| `FOREIGN_RSU` | RSUs from a foreign parent company | **needs_human** (Schedule FA, out of scope) |
| `VDA_TRADES` | crypto trades in AIS | **needs_human** |

## 6. Benchmark (the evidence) — `bench/`

Run: `python -m bench.run_bench --cases data/cases --repeats 3`.

**Systems compared**
1. **Filed** — the full agent pipeline.
2. **Single-prompt baseline** — all document text in one prompt; the model returns form, regime, taxable income and final tax as JSON. Same model, same documents. This is "just ask ChatGPT".
3. *(Optional, if time)* **Filed without reconciliation** — ablation showing the reconcile step matters.

**Metrics** (all per system, mean ± std over repeats, plus per-trap breakdown):
- **Exact return rate** — final tax payable/refund within ₹10 of truth.
- **Mean absolute tax error (₹)**.
- **ITR form accuracy** and **regime accuracy**.
- **Trap handling rate** — per trap code, % handled correctly.
- **Escalation recall** — of items that truly need a human, % escalated.
- **Escalation precision** — of escalations, % that truly needed a human.
- **False-automation rate** (headline) — returns marked `ready_to_file` that are wrong. This is the number a real firm lives or dies by.
- **Hands-off rate** — % of returns finished with zero human touches.
- **Cost per return** (₹, from token counts and the provider's published price; ₹0 on the free tier but report tokens) and **time per return**.

**Outputs:** `bench/results.md` (tables + an honest "where it fails and why" section), `bench/chart.png` (one clear grouped bar chart: Filed vs baseline on the 4 key metrics), raw per-run JSON in `runs/` (git-ignored, but keep a summary CSV committed).

Free-tier limits: run the benchmark over several sessions, resumable (skip case/repeat pairs that already have a result file). Start it by **28 Nov**.

## 7. Demo app (`app/main.py`, Streamlit)

Three pages, clean and minimal:

1. **New return** — pick a sample client (or upload files) → "Prepare return" → live step-by-step progress (intake → reconcile → decide → compute → review), flags appear as they are found, then the result: ITR form, regime comparison table (old vs new, highlighting the saving), tax payable/refund, download ITR JSON, the client email.
2. **CA queue** — the firm view: all clients, status (ready to file / needs you), each escalation as a one-line question with the evidence and Approve / Edit buttons. Approving re-runs compute and moves the case to ready.
3. **Results** — the benchmark table and chart, read from `bench/results.md`.

The firm angle is the point: "50 clients came in, 41 returns were finished with no human, 9 questions went to the CA, about 15 minutes of human time in total."

## 10. Pitch notes (for `docs/pitch.md`)

- **Problem:** filing is confusing, mismatches with AIS trigger notices, a CA costs ₹1.5k–5k and is busy in July.
- **Customer:** salaried and first-job people, small investors; later freelancers (ITR-4) and NRIs.
- **Product:** not a tool — the firm. Upload documents, get a finished return; a CA signs off only on flagged questions.
- **Why now:** AIS made every taxpayer's data available in one place; models can now read messy documents reliably; the agent does the clerical 90%.
- **Business:** ~₹499 per return vs ₹1.5k–5k; CA time per return falls from ~1 hour to minutes (state as an estimate); recurring revenue from notice replies, advance-tax reminders, next year's filing.
- **Moat:** the reconciliation knowledge base and the escalation data (which questions humans actually needed to answer).
- **Evidence:** our benchmark numbers.
